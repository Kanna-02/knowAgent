# 路线图

本路线图以“完整目标设计、分阶段形成可验证能力”为原则。多系统是基础能力，不以单系统 MVP 限制产品结构；ESB 仅作为首批真实数据和评测集。

## 1. 阶段总览

| 阶段 | 目标 | 主要范围 | 状态 | 阶段验收 |
| --- | --- | --- | --- | --- |
| Phase 0 | 初始化与决策门禁 | 需求、设计方向、技术选型、架构 | 已完成 | 文档确认，技术和架构方案通过门禁 |
| Phase 1 | 多系统知识基础 | 本地账号、RBAC、系统管理、管理后台、四类文档处理 | 进行中（1/6） | 两个系统可隔离管理知识，文档可追溯 |
| Phase 2 | 问答与工单闭环 | 检索、带引用回答、拒答、内置工单、审核回流 | 未开始 | 端到端主流程和 AC-001 至 AC-007 通过 |
| Phase 3 | 质量与运营增强 | 混合检索、Rerank、多轮、通知、版本、分析、审计 | 未开始 | 质量指标、降级和运营流程稳定 |
| Phase 4 | 内网交付与扩展 | 非 Docker Linux 部署、安全加固、监控备份、SSO 准备 | 未开始 | 可重复部署、回滚和运行维护 |

## 3. Phase 0 - 初始化与决策门禁

目标：

1. 固化产品应用定位、多系统边界、角色、流程、部署约束和验收基线。
2. 对前后端、数据、检索模型、任务机制、认证和非容器化部署给出候选方案并完成选择。
3. 形成可实现、可测试、可追溯的架构设计。
4. 完成 `knowledge-rag` 可复用资产盘点，明确可迁移、需重构和禁止迁移边界。

交付物：

1. 需求澄清、路线图、前端设计、开发原则和追溯矩阵。
2. 技术选型记录和性能权衡。
3. 系统架构、模块边界、接口、数据流和部署视图。
4. 来源项目迁移评估及迁移门禁。

验收标准：

1. P0/P1/P2、角色、端到端流程和 AC 均无关键空白。
2. 技术选型完成 2-3 方案比较并得到用户确认。
3. 架构方案得到用户确认后才进入代码实现。
4. 不以来源项目 README、禁用测试或骨架 TODO 作为可迁移成熟度证明。

## 4. Phase 1 - 多系统知识基础

功能范围：

1. 用户端/管理端独立登录表单、统一账号认证、用户 SQL 批量导入、管理员后台新增、首次改密、三角色 RBAC 和 SSO 适配边界。
2. 多业务系统管理、系统负责人配置和前台系统选择。
3. 用户端与管理后台基础导航、状态和错误处理。
4. 先定义统一 `SourceLocator`，再实现 `.docx`、文本型 `.pdf`、`.md`、`.xlsx` 的结构化解析、切分和精确引用定位。
5. 对象存储、持久化入库任务、幂等、阶段进度、失败重试和进程重启恢复。
6. 文档版本、发布状态和基于 `system_id` 强过滤的知识隔离基础模型。

验收标准：

1. AC-001、AC-002、AC-003、AC-009 的 Phase 1 部分通过，包括错误入口、默认密码首次改密和服务端越权测试。
2. 至少两个系统和四类样本文档完成真实持久化集成测试，并通过任务重启恢复测试。

## 5. Phase 2 - 问答与工单闭环

功能范围：

1. 关键词与向量基础召回、证据组织、回答生成和来源引用。
2. 证据充分性决策；不足时记录原因、拒答并自动创建内置工单。
3. 按系统分派、处理、追加、关闭、重开和审核入库。
4. 审核发布后的知识重新索引、来源追踪和历史引用快照保留。

验收标准：

1. AC-004 至 AC-007 通过。
2. 使用 ESB 真实问题集跑通问答、拒答、工单和回流的完整链路。

## 6. Phase 3 - 质量与运营增强

功能范围：

1. 混合检索调优、Rerank 和显式降级。
2. 多轮上下文、意图识别、提示词和检索配置版本。
3. 公司通知 API、失败重试和通知记录。
4. 文档生命周期、对话分析、高频问题、知识缺口和审计。

验收标准：

1. AC-004、AC-005、AC-008、AC-009、AC-011、AC-013、AC-014 在质量增强链路上通过。
2. 外部服务、持久化和异步流程均有真实集成验证，不以 mock 代替。

## 7. Phase 4 - 内网交付与扩展

功能范围：

1. 无 Docker 的 Linux 安装、配置、systemd 进程管理、Nginx 反向代理、升级、备份和回滚流程。
2. 面向宿主机进程、PostgreSQL、Redis、对象存储和模型服务的日志、指标、告警、容量与安全加固。
3. 公司 SSO 接入准备，以及更多业务系统的运营接入流程。

验收标准：

1. AC-010、AC-012 通过，并在类生产 Linux 环境完成一次全新安装和一次回滚演练。
2. 形成系统负责人可执行的知识接入和日常运营清单。

## 8. 路线图调整规则

- 不因“首版必须简单”移除多系统边界，但允许按阶段逐步完成同一完整方案。
- 每阶段必须有独立可观察结果；未通过验收不得把问题隐藏到下一阶段。
- 模型、框架、数据库扩展、任务系统和部署方式必须先通过技术选型门禁。
- 需求优先级或阶段范围变化时，同步更新需求文档和追溯矩阵。
