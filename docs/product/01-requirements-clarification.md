# 需求澄清：企业内部智能客服 Agent

本文档记录初始化阶段已确认的产品边界。项目暂名 `KnowAgent`，正式名称不影响当前设计。

## 1. 项目一句话描述

KnowAgent 是面向公司内部人员的 Web 智能客服产品，按业务系统隔离和管理知识，使用可溯源的 RAG 问答降低重复沟通成本，并通过内置工单和人工审核形成知识持续回流闭环。

## 2. 项目定位

- 定位：产品应用，不是面向其他系统或 Agent 的基础设施服务。
- 判定依据：主要用户是公司内部终端用户，核心入口是 Web 会话和管理后台，权限围绕用户角色与业务系统展开。
- 首版边界：直接支持多个业务系统；用户提问前选择目标系统，检索严格限定在该系统知识空间。
- 首批数据：优先导入 ESB 文档并使用 ESB 真实咨询问题验证效果，但多系统能力不是后续版本才补充的功能。

## 3. 目标用户

| 用户类型 | 使用场景 | 核心诉求 |
| --- | --- | --- |
| 普通用户 | 使用批量导入的本地账号登录，咨询 ESB、数据交换等系统问题 | 快速得到准确答案、查看来源、跟踪未解决问题 |
| 系统负责人 | 使用用户端账号登录，维护所属系统知识、处理系统工单、审核新增答案 | 减少重复沟通，及时发现知识缺口 |
| 平台管理员 | 使用独立管理入口登录，新增管理员并管理账号、系统和全局配置 | 保证平台安全、稳定、可治理 |

## 4. 核心问题

本项目解决：

1. 已有文档难以在实际对接场景中快速转化为准确答案。
2. 各系统负责人每天需要重复识别和回答相似问题，人工沟通约占 1-2 小时。
3. 无答案问题缺少统一分派、通知、跟踪和知识回流机制。
4. 现有沟通过程难以统计高频问题和文档缺口。

本阶段不解决：

1. 不替代公司现有通用工单系统，也不与其集成。
2. 不从零训练 Embedding、Rerank 或大语言模型；项目负责集成和运营成熟模型或推理服务。
3. 不建设面向其他应用的多租户 Agent 基础设施平台。
4. 不把扫描 PDF OCR、旧版 `.doc`/`.xls` 作为首批格式基线，是否支持由样本文档和技术选型决定。

## 6. 关键业务流程

### 6.1 文档入库

```text
系统负责人选择所属业务系统
-> 上传文档
-> 系统异步解析、切分、索引
-> 负责人查看处理状态和错误
-> 发布成功版本
-> 文档进入该业务系统的可检索知识空间
```

### 6.2 问答与引用

```text
普通用户登录并选择业务系统
-> 输入问题
-> 系统识别意图并仅检索该系统知识
-> 对证据排序并判断是否足以回答
-> 返回带来源引用的答案，或明确拒答并创建工单
```

### 6.3 工单与知识回流

```text
系统因证据不足创建工单
-> 按业务系统分派负责人并调用通知 API
-> 负责人处理并补充答案
-> 用户收到回复，可追加问题或在关闭后重开
-> 负责人或管理员审核答案
-> 通过后生成带工单来源的知识条目并重新索引
-> 后续相似问题可直接命中
```

## 7. 权限与角色

| 角色 | 可执行操作 | 不可执行操作 |
| --- | --- | --- |
| 普通用户 | 从用户入口登录；查询已发布系统、发起会话、查看引用、查看和回复自己的工单 | 进入管理后台、上传/发布知识、处理他人工单、管理账号和系统 |
| 系统负责人 | 从用户入口登录；具备普通用户能力，并管理被分配系统的文档、知识和工单 | 管理未分配系统、创建管理员或修改平台级配置 |
| 平台管理员 | 从管理入口登录；新增管理员，查看用户导入结果，管理系统、负责人、全局配置和审计 | 无权绕过审计直接修改生产数据 |

用户端与管理端使用不同登录表单和路由，但共享账号表、密码策略、会话服务和审计逻辑。用户账号通过受控 SQL/导入脚本批量写入；管理员账号由已登录管理员在后台新增。系统负责人是用户账号通过系统负责人映射获得的权限，不建立第三套登录体系。

## 8. 主要数据对象

| 数据对象 | 关键内容 | 说明 |
| --- | --- | --- |
| 用户与角色 | 账号、Argon2id 密码摘要、状态、角色、账号来源、首次改密标记、会话版本 | 用户批量导入；管理员后台创建；预留 SSO 外部身份标识 |
| 业务系统 | 名称、标识、状态、负责人 | 所有知识、会话和工单必须关联业务系统 |
| 文档与版本 | 文件元数据、对象存储键、校验值、解析状态、版本、发布状态 | 原文件进入现有对象存储 |
| 知识片段 | 文本、系统、文档版本、向量引用、统一来源定位 `SourceLocator` | 定位信息至少覆盖 PDF 页码、Word 标题路径、Markdown 标题路径、Excel 工作表与单元格范围 |
| 会话与消息 | 用户、业务系统、角色、内容、时间、模型运行信息 | 支撑多轮上下文和分析 |
| 答案与引用 | 回答、证据片段快照、引用位置、置信状态、拒答原因 | 文档更新后历史回答的引用文本和定位仍可复核 |
| 入库任务 | 文档版本、任务状态、阶段进度、重试次数、错误和租约 | 任务持久化，进程重启后可恢复，不依赖单进程内存队列 |
| 工单与回复 | 提问人、系统、负责人、状态、会话上下文、回复 | 内置轻量工单，不对接外部工单系统 |
| 知识候选 | 工单答案、审核人、审核状态、发布版本 | 审核通过后才能进入正式知识库 |
| 通知记录 | 接收人、渠道、模板、状态、重试次数 | 对接公司通知 API |
| 提示词版本 | 场景、版本、内容、启用状态、变更说明 | 不硬编码在业务代码中 |
| 审计记录 | 操作者、动作、对象、时间、结果 | 覆盖权限、知识和工单关键操作 |

## 9. 外部接口与部署约束

- 公司已有大模型 API，可发送内部知识；是否兼容 OpenAI 协议仍待确认。
- 公司目前不提供 Embedding 和 Rerank API，需要在技术选型阶段比较本地模型推理、独立内部服务等成熟方案。
- 公司通知 API 的真实契约尚未提供；当前以管理员可配置的 HTTP JSON Provider 适配地址、鉴权密钥引用、受控模板、成功状态码、超时与重试参数，真实鉴权、限流和回执协议到位后通过独立适配器或配置完成联调。
- 目标环境为公司内网 Linux，明确禁止 Docker。
- 已有 PostgreSQL、Redis 和对象存储，版本、连接方式、容量及对象存储协议待确认。
- 文档解析和索引必须采用持久化后台任务，列表类接口必须分页；任务需支持幂等、进度、重试和进程重启恢复，不能仅依赖进程内 `@Async` 或内存队列。
- Embedding、Rerank、LLM 和通知调用必须通过独立 provider 接口适配，业务领域对象不得直接依赖 Ollama、TEI 或特定 SDK 类型。
- 向量维度、模型名称和检索参数必须与模型配置联动，不得在实体、SQL 和服务中重复硬编码。
- 用户与管理员采用不同登录入口，但认证实现必须共用；批量用户默认密码不得以明文或可逆形式写入 SQL，只能写入受控生成的 Argon2id 摘要，并设置 `must_change_password=true`。
- 首个管理员通过一次性 CLI 或受控初始化 SQL 创建；后续管理员由后台新增。默认密码首次登录后必须修改，未修改前只能进入改密和退出流程。

## 10. 初始验收标准

| AC | 可验证标准 |
| --- | --- |
| AC-001 | 批量导入用户可从用户入口登录，后台新增管理员可从管理入口登录；默认密码首次登录必须修改；错误入口、禁用账号和三种角色的越权访问均被服务端拒绝并通过自动化或接口测试验证。 |
| AC-002 | 至少创建两个业务系统；同一问题在不同系统中只使用对应知识，跨系统知识泄漏为 0。 |
| AC-003 | `.docx`、文本型 `.pdf`、`.md`、`.xlsx` 各至少一个样本完成解析、索引和精确引用定位；引用分别可回到 Word 标题路径、PDF 页码、Markdown 标题路径、Excel 工作表与单元格范围；失败文件显示可诊断原因。 |
| AC-004 | 基于至少 50 个 ESB 真实问题的初始评测集，答案正确率不低于 80%，引用支持率不低于 95%；文档发布新版本后，历史答案仍保留当时的引用片段快照。 |
| AC-005 | 无知识支撑的测试问题拒答召回率不低于 90%，每次可靠拒答均生成可跟踪工单，不生成无引用事实答案。 |
| AC-006 | 工单可完成自动分派、回复、追加、关闭和重开，关键状态转换均有审计记录。 |
| AC-007 | 工单答案未经审核不可进入知识库；审核发布后 5 分钟内可被重新检索，并保留工单来源。 |
| AC-008 | Rerank、向量检索或模型服务不可用时按规则降级，用户收到明确状态，系统不返回伪造答案。 |
| AC-009 | 文档处理、工单和审计列表支持分页；批量文档处理不会阻塞交互请求；处理进程重启后，未完成任务可自动恢复或进入可人工重试状态。 |
| AC-010 | 项目可在无 Docker 的目标 Linux 环境按文档部署，密钥不进入代码仓库。 |
| AC-011 | 分析页可按业务系统和时间范围查看问题量、未解决量、高频问题和知识缺口，统计结果可追溯到对应会话或工单。 |
| AC-012 | 接入 SSO 后，合法公司身份可登录并映射本地用户；禁用用户不可登录；SSO 不可用时的本地管理员应急入口符合安全策略。 |
| AC-013 | 在包含至少 20 组改写问题和无关问题的测试集中，相似问题/重复工单识别召回率不低于 80%，误报率不高于 10%。 |
| AC-014 | 创建工单后正确通知对应系统负责人，负责人回复后通知提问人；临时失败按配置重试，永久失败可查询并可人工重试。 |

上述指标是初始化基线，可在形成真实评测集后调整，但任何调整都必须记录原因，不能删除失败样本来提高指标。

## 11. 已确认与待确认事项

已确认：

- 首版直接支持多系统，ESB 是首批数据而非单系统产品边界。
- 保留用户和管理员双方登录：用户账号通过受控 SQL/导入脚本批量创建并使用默认密码首次改密，管理员账号由后台新增；两端共用认证服务并预留 SSO 接口。
- 使用内置轻量工单，不对接现有工单系统。
- 管理员/负责人补充答案，审核后进入知识库。
- 通过公司通知 API 发送消息。
- 通知首版采用可配置 HTTP JSON Provider、PostgreSQL 事务 Outbox 和 Celery 独立队列；数据库只保存密钥环境变量引用名，不保存密钥明文。
- 非 Docker、内网 Linux 部署，可使用现有 PostgreSQL、Redis 和对象存储。
- UI 采用克制、高效的内部工具方向。
