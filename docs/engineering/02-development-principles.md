# 开发原则

本文档补充根目录规则，约束企业内部智能客服 Agent 的产品和工程实现。

## 1. 产品原则

1. 产品目标完整设计、分阶段交付，每个阶段都必须形成可验证能力。
2. 多业务系统是第一版基础边界，所有知识、会话、引用和工单必须关联业务系统。
3. 回答必须基于可展示证据；证据不足时拒答并进入工单，正确拒答优先于流畅编造。
4. 工单答案必须经过审核才可成为正式知识，并保留来源与版本。
5. 用户端强调快速问答和问题跟踪，管理端强调批量操作、状态可见和异常处理。
6. 不为了展示“复杂 Agent”而增加无业务收益的规划、工具调用或多智能体链路。

## 2. 技术原则

1. Embedding、Rerank 和 LLM 使用成熟模型、运行时或服务；“自建”指自主管理集成与推理服务，不从零训练算法。
2. 文档解析、检索、生成、工单、通知和权限保持清晰边界，具体模块在架构阶段确认。
3. LLM、Embedding、Rerank、对象存储和通知均通过可替换适配接口接入。
4. Rerank、向量检索和模型调用必须有显式降级与超时，不能让单个外部能力阻断全部问答。
5. 提示词、模型名、阈值、top-k、批大小、超时、重试和文件限制必须配置化。
6. 技术栈、任务执行方式、模型运行方式和非 Docker 部署方案必须完成多方案比较后确认。

## 3. 数据与检索原则

1. 系统标识是知识隔离的强制过滤条件，不能只依赖提示词要求模型自行区分。
2. 文档原文件、解析结果、片段、向量、引用位置和版本必须可追溯。
3. 解析与索引采用后台任务，写入过程必须幂等，失败可重试且不发布半成品索引。
4. 引用应定位到可核验位置：PDF 页码、Word 标题/段落、Markdown 标题、Excel 工作表与单元格区域。
5. 文档更新、下线和重建索引必须避免旧版本与新版本同时污染检索结果。
6. 工单回流知识与原始文档知识区分来源，但进入同一受控检索链路。

## 4. 权限与安全原则

1. 首版保留用户端和管理端两套登录表单，但必须共用账号表、认证服务、密码策略和会话机制，并预留 SSO 适配边界。
2. 权限必须在服务端校验；前端隐藏按钮不能替代授权。
3. 系统负责人只能维护所属系统知识与工单，平台管理员的高风险操作必须审计。
4. 密码只保存 Argon2id 强哈希；批量用户的默认密码必须首次登录修改，不得把明文默认密码、API 密钥或数据库凭据写入仓库和日志。
5. 文档内容、提示词输入和用户问题均视为不可信输入，必须防范 prompt injection 和文件解析攻击。
6. 日志不得记录完整文档、访问令牌、密码或不必要的会话正文。
7. 用户账号由受控 SQL/导入脚本批量创建，管理员账号由后台创建；两类入口必须校验允许的角色，禁止仅靠前端路由隔离。

## 5. API 与错误原则

1. API 契约、响应结构、分页方式和错误码在架构阶段统一确认。
2. 入参必须校验，业务错误与系统错误分离，错误信息可诊断但不泄露内部细节。
3. 列表、会话、消息、工单、文档和审计接口必须分页，默认限制与最大限制配置化。
4. 外部 API 必须设置连接/读取超时、有限重试、幂等键和失败记录；不可无限重试。
5. 大文件上传、解析和索引状态使用异步流程，避免长连接占用 Web 请求线程。

## 6. 前端与交互原则

具体风格与 token 以 `docs/product/15-frontend-design.md` 和 `15-frontend-design-tokens.json` 为准。

1. 产品是安静、紧凑、面向重复操作的内部工具，不制作营销首页。
2. 问答页优先展示系统选择、会话内容、引用和工单状态；管理页优先使用表格、筛选和批量操作。
3. 不使用卡片嵌套卡片，不用装饰性渐变或大面积单色制造视觉噪声。
4. loading、empty、error、success、disabled 和权限不足状态必须完整。
5. 文档预览、图表、富文本等重型能力按需加载，并先通过技术选型门禁。
6. 桌面端优先，同时保证移动端查询、查看引用和跟踪工单的基本流程可用。

## 7. 性能原则

1. 文档解析和 Embedding 批处理，限制并发、批大小、文件大小和队列容量。
2. 为系统、状态、负责人、更新时间等高频过滤字段规划索引，避免 N+1 查询。
3. 会话、消息、工单、文档和审计采用分页或增量加载；长列表需要评估虚拟化。
4. 前端按路由分包，管理后台的图表、预览和编辑能力不得进入问答首屏主包。
5. 记录解析耗时、索引耗时、检索耗时、生成耗时、失败率、降级率和队列积压。
6. 性能优化以测量结果为依据；暂缓项必须记录原因和后续补点。

## 8. 质量与测试原则

1. 遵循 `QUALITY_RULES.md` 的静态检查、类型、覆盖率和失败处理规则。
2. 核心模块覆盖正常、边界和异常路径；系统隔离、拒答、工单状态机和权限属于高风险测试重点。
3. 外部服务、数据库、缓存、对象存储和异步流程必须有集成测试，不能只使用 mock。
4. 公司不允许 Docker，因此集成测试使用隔离测试 Schema、Bucket 和测试端点，并在类生产 Linux 环境验证核心链路。
5. 以固定评测集比较检索、提示词和模型版本，不删除失败样本来提高指标。

## 9. 部署原则

1. 目标是公司内网 Linux，禁止把 Docker 作为运行前提。
2. 构建产物、配置、数据库迁移、静态资源和进程管理方式必须可重复执行。
3. 复用现有 PostgreSQL、Redis 和对象存储前，必须确认版本、协议、权限、容量和备份责任。
4. 上线前必须提供启动、停止、健康检查、日志、升级、备份、回滚和故障排查说明。

## 10. 技术选型门禁

以下事项不得在初始化阶段直接拍板：前后端框架、ORM/数据库访问方案、任务机制、向量存储方式、Embedding/Rerank 模型与运行时、认证令牌机制、通知客户端、文件解析库、进程管理和监控方案。

每项重要选择必须比较 2-3 个方案，记录性能、成本、运维复杂度和风险，得到用户确认后写入 `docs/engineering/04-tech-decisions.md`。
